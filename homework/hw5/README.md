## 1. Маппинг в БД: Возьмите ваш агрегат Order и спроектируйте его хранение в реляционной БД (PostgreSQL). Напишите DDL-скрипты (CREATE TABLE… ) для всех необходимых таблиц. Объясните, как вы сохранили Value Objects.

Объяснение: Объект-значение Деньги(Modey) используется в сущностях Товар(Product) и Линия заказа(OrderLine). В обоих случаях Объект-значение Деньги сохнаняется в таблице сущности в двух полях price_amount numeric(12, 2) и price_currency varchar(3). Объекту-значению Деньги не требуется идентификатор и отдельная таблица для хранения так-же не требуется. Возможный так-же вариант хранить Деньги в одном поле с типом JSON.

## 2. Оптимистичные блокировки: Добавьте в таблицу Orders поле Version. Опишите (или покажите в псевдокоде SQL), как будет выглядеть запрос UPDATE, реализующий механизм оптимистичной блокировки для предотвращения «потерянных обновлений».

## 3. Проектирование Саги (Saga):

Спроектируйте распределённый бизнес-процесс «Оформление и оплата заказа», затрагивающий минимум 3 контекста (например, Orders, Payments, Notifications).
Опишите по шагам позитивный сценарий (happy path).
Опишите компенсирующие транзакции для негативного сценария (например, если оплата не прошла после создания заказа).

## 4. Идемпотентный обработчик: Напишите псевдокод обработчика события OrderPaidEvent на стороне сервиса Notifications. В нём должна быть реализована логика идемпотентности (например, через проверку в БД уже обработанных ID событий), чтобы уведомление не отправлялось дважды.
